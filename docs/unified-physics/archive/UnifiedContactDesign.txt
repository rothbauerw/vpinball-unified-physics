UNIFIED CONTACT SYSTEM - DESIGN (draft 2026-10-11, for review before code)
==========================================================================

Save point: branch save/pre-unified-contact (commit 4216f7e34, local only). The old stepping stays on disk until the new system has parity.

1. Goal
-------
One contact system owns every ball. Stock VPX does not handle any ball: no hit-time search, no impulse collisions, no position pushes, no static-contact pass.
Each physics cycle every body gets ALL the forces acting on it summed before anything moves, so forces balance at every instant:
ball-surface, ball-ball, ball-flipper, ball-band, ball-disc, magnets, gravity, nudge, coils, springs, motors.

2. Model: bodies, interactions, islands
---------------------------------------
Body        anything with state that moves: Ball (3D, spin), Bat (one rotation about the pivot, coil + spring + stops), BandNode, Disc (one rotation),
            SlingPlate, Plunger, later targets and gates. SI units inside. Holds mass or inertia, state, a force/torque accumulator, and a pointer to the VPX object
            it writes back to. Static geometry is not a body: it is a Surface.
Surface     static geometry that bodies touch (playfield mesh or plane, post and wall rubbers, wall and primitive meshes, ramps). Provides Probe(body) -> nearest
            point, normal, curvature, material. Replaces the HitRubber "host" role (the playfield and the turntable are not rubbers).
Interaction a pair (body, body) or (body, surface) that can exert force: a ContactLaw instance plus its persistent state (shear spring, pair state).
Source      anything that is not a pair: gravity, nudge, magnets, coil torque, spring, motor. Adds to one body's accumulator.
Island      connected component of the interaction graph (union-find each cycle, like the ball clusters). An island is stepped on its own substep.

3. The step (replaces PhysicsSimulateCycle once stock is removed)
-----------------------------------------------------------------
ContactSystem::Step(cycle):
  1. Sync: read state of every VPX object that owns a Body into the Body (position, velocity, spin, flipper angle, ...).
  2. Broadphase: persistent candidate lists (Verlet lists): per body, the surfaces and bodies within reach + margin; rebuilt only when a body has moved more than
     margin/2 since the last build (not every cycle, not every sub-interval).
  3. Islands: union-find over interactions that can touch this cycle (gap < reach + 2 * vrel * cycle).
  4. Per island: h = f(stiffest contact omega, fastest approach, speed cap so no body moves more than a fraction of its radius per substep); n = ceil(cycle / h).
     for each substep:
        clear accumulators
        every Interaction: evaluate the law on the CURRENT states, add +F to one body and -F to the other (Newton's third law by construction)
        every Source: add its force
        integrate every body in the island (semi-implicit Euler)
  5. Write back to the VPX objects; fire events (see 5).
There is exactly one call per 1 ms cycle: no splitting at hit times, no per-owner passes, no ownership flags (m_bandOwner, m_rubberOwner, m_rubberAdvanced go away).

4. Contact law interface (force or constraint)
----------------------------------------------
Every law implements   Evaluate(const View &a, const View &b, double h, State &st, Out &out)
Out is either
   Force      {F on a, point, torque on a, torque on b}        (compliant: Hertz + damping + Mindlin + twist + rolling resistance, today's ContactCore)
   Constraint {rows: normal and friction Jacobians, bias, impulse bounds}   (rigid; NOT implemented in phase 1; the interface only reserves it)
Phase 1 uses Force for everything: the validated model. A rigid solve for the stiff pairs (steel-steel, steel-wood) is added later only if measurements show the
stiff contacts need it (cost or stability), as impulses in the same island step after the compliant forces have been summed into the predicted velocity.
The alternative for the stiff pairs, an implicit (soft-constraint) integration of the same spring, also fits behind the same interface.

5. Events, sensors and mechanisms
----------------------------------
Events (script Hit/UnHit, hit speed, ball-ball callback, rumble, EOS/BOS, switch changes) are DEFERRED: during the substeps a contact-state change appends a record
(type, object, speed, time inside the cycle); after write-back the queue is dispatched in order. Scripts never run inside the step (they may move or delete balls, kick,
change solenoids). Cost: up to 1 ms latency between a hit and the script's reaction (decided 2026-10-11: acceptable).
What an object is:
   Opto / pure sensor   overlap test, event, no force (an optical switch)
   Mechanical switch    a Body with a spring (micro-switch, wire trigger, rollover): the ball deflects it with real force; the switch closes at a deflection threshold;
                        the event comes from the body's state. Not every trigger has force and not every one is a sensor: both kinds exist and are chosen per object.
   Kicker               sensor + mechanism: capture (a hold constraint) and eject (impulse source)
   Spinner, gate        Bodies with one rotational DOF (like the disc)
   Drop target          Body (solenoid reset); stand-up target: Surface + switch (a mechanical switch behind it)
Rendering, the editor UI, VR, ball control and the script properties read only the public VPX state, which is written back at the end of every cycle (audit of all
consumers of physics state is step 0).

6. Naming (code follows what it models)
---------------------------------------
RingAdvanceAll -> ContactSystem::Step      RingBall -> (disappears: every ball is in the system)      HitRubber host surfaces -> ContactSurface
m_bandOwner/m_rubberOwner/m_rubberAdvanced -> removed                  ContactCore -> HertzMindlinLaw (file rubbercontact.h keeps the law)
New files: src/physics/contactsystem.{h,cpp}, contactbody.h, contactsurface.h. The old files stay until their function has moved.

7. Engine selection and migration
---------------------------------
Stock physics stays in the repository and stays selectable; old tables keep working unchanged. The engine is chosen PER TABLE, stored in the .vpx (decided 2026-10-11),
at table load. Unified tables are one-way: "Convert to Unified" in the editor (alternate UI that manages all unified features: materials, flippers, rubbers, bands, slings,
magnets, turntables, ...) writes the unified configuration INTO the .vpx and keeps a backup of the original file. All unified settings live in the .vpx, not in an ini
(the ini was a convenience for building the features without touching .vpx files; it is retired for unified tables). Open: how the new records are tagged in the .vpx
(older VPX versions must ignore them) and the editor panel layout.
The unified engine takes geometry from the table parts through a new interface (each part supplies its contact surfaces / bodies) instead of the stock HitObjects.
Decided simplifications inside the unified engine: no hit-plane playfield (the implicit mesh playfield is the only playfield; a plane is a degenerate mesh); no stock hit
search, impulses, position pushes or static-contact pass. More to drop as we find them (flag each when found).
DEV FALLBACK (decided 2026-10-11): until an object type is converted, the unified engine still runs the stock hit search for it; problems from that mix are ignored
until that type's migration step. The fallback is removed after step 5.
Steps (each compared with the save point in the same harness):
  0. Audit of every consumer of physics state (renderer, VR, ball control, kicker/bumper/trigger parts, script properties, plugins); engine switch at table load.
  1. Bodies + islands + step loop with balls only: playfield mesh, rubber posts and walls, the disc, ball-ball, magnets. Parity with the save point on: tt14_m28_d0,
     cradle3, rest_flat, drop, slow4, pinch. (gsw15f, the kicker-capture test, moves to step 5; the sling regressions move to step 3.)
  2. Flipper as a Bat body (coil, spring, stops, rubber contact, nudge).
  3. Band nodes and sling plates as bodies.
  4. Generic mesh contact for walls, primitives and ramps; part-to-surface interface.
  5. Kickers, targets, mechanical switches, plunger, gates, spinners.
  6. Alternate editor UI and .vpx persistence (can start earlier for the keys that exist); stock stays available for old tables.

8. Performance rules
--------------------
Persistent candidate lists; one probe per interaction per substep; islands at rest run at the stiffness-limited step or sleep (no force change, no motion for N cycles);
no allocation in the step (reused buffers); measure the per-cycle maximum, not only the average (p99 histogram is on the parking lot).

9. Known risks / unknowns
-------------------------
* Stiff steel contacts need 2-6 us steps in compliant form (cost); mitigation as in 4, decided by measurement.
* Mass ratio ball : bat in one island (bat driven by coil): explicit integration of the bat with a stiff rubber contact needs the same small step as the ball.
* Fast balls (plunger shot, 10+ m/s): the speed cap on the substep is the only tunnelling protection; verify against thin posts and walls.
* Every stock object type needs a force-model equivalent before step 6; until then the flag stays.

10. Units (decided 2026-10-11)
------------------------------
Real-world units at every boundary (files, UI, new script properties): metric canonical (mm, m/s, N, g, degrees, us), imperial only as a display setting of the editor UI.
VPX units exist only in the sync/write-back adapter and for legacy script properties (kept as they are; real-unit properties are added beside them). Ball mass in grams.
Names carry physics only (no machine names).

11. Overlap at first sight: the standard for every model   (AGREED with the user 2026-10-26, point by point; point 1 built, the rest not built)
-----------------------------------------------------------------------------------------------------------------------------------------
Why. A ball found inside a surface the first time the contact system looks is not a contact with a history: its compression is an artefact of how late it was found. A force law applied to that
depth gives a force the real contact never had (Hertz on steel: 169 um is 37 kN). Measured in the user's session of 2026-10-26 (Rubber Test 2, 35 bumper engagements): 33 started with no overlap
(out speed <= 1 m/s, force <= 1.5 kN); the two that started overlapped (70 and 169 um) left at 1.8 and 4.5 m/s with 7 and 68 kN, from approaches of 0.29 and 0.33 m/s. In the 169 um case the engage seat
(ball moved back along its own velocity, surface not moved) made the overlap grow on each of 3 passes (55, 68, 169 um) against the slanted steel ring. Unified solutions never use stock (user rule):
every case below is resolved inside the contact system.

1. PREVENT (agreed, BUILT 2026-10-26). Engagement uses the closing speed relative to the surface: ball closing speed + the surface's bound; engage when gap < closing x 2 x cycle + release gap; the host-box
   prefilter and the face refresh widen by 2 x bound x cycle. Every part answers ContactMovingPart::SurfaceSpeedBound(cycle) (pure virtual): its present speed plus what its own drive and springs can add in a
   cycle. Hinge parts: (|omega| + (gravity torque + cams + springs) / I x cycle) x reach + a driven stop's rate x reach. Bumper: ring = |v| + (coil force at full current, plunger closed + return spring) / m x
   cycle, skirt rim likewise; a sleeping bumper counts the ring's acceleration (Solenoid can start it). Static surfaces answer 0. A held ball keeps its engagement while gap < release gap + bound x cycle
   (the 2 mm 'moving away' clause grows by the same). Arrival-time steps (BallStep) use the same bound. Not covered: the turntable disc's rim speed; a surface faster than its stated bound (the report shows it).

2. REWIND THE ISLAND (agreed, not built). An overlap found at engagement was born inside the last sub-interval. Find the time t* in it when the gap was zero with BOTH the ball and the part where they really
   were (the part evaluated in a scratch copy of its saved state), restore the whole island to t* (the part, every ball touching it, anything coupled), and step it forward with the new ball in it. The contact
   starts at zero depth with the real velocities and the force law does the rest. Nothing is seated; no velocity is edited. A second ball is handled the same way: the island is rewound, not the ball alone.
   * Order inside a sub-interval (agreed): Step (held balls, parts) -> UpdateDisplacements (free balls) -> engagement / overlap check with the rewind -> dispatch of ALL queued events (the step's queue and the
     part events now fired inside PartAdvance). Nothing has run when a rewind happens, so there is nothing to undo, and no latency is added. This is the order of stock VPX.
   * Save / restore (agreed): ContactMovingPart::SaveState / RestoreState, dynamic values only, no allocation. Parts first (bumper, gate, spinner). An island with a bat, band or disc keeps the ball-only
     rewind until that type implements it (reported, never stock).
   * Cost (agreed): save every sub-interval if the measured cost is low (snapshot_us column in VPX_CONTACT_TIMING, judged by the worst cycle); otherwise only when a free ball is within reach of a part (part
     box + ball radius + (ball speed + bound) x 2 cycles). A sleeping part saves its flag only.
   * Stock (agreed): stock collision impulses are applied at the END of the sub-interval, after the check, so none falls inside the rewound span.
   * Chained replays (agreed): rewind to the EARLIEST first contact among the pending overlaps (progress is guaranteed); bisect on the gap, part in a scratch copy, to arrival_depth_um (2 um); the new body joins
     the island and the existing arrival-time stepping handles later contacts in the replay; a further boundary replay only for yet another free body found overlapping (cap = free balls and parts near + 1).
     Not covered: a ball through a thin rim and out again inside one sub-interval (point 1 prevents it).

3. VELOCITY (retired): point 2 edits no velocity.

4. (withdrawn: no stock hand-back, no stock safety net.)

5. REPORT (agreed, rule 8). Always on, each a WARN in the log and a playfield notification once per cause per table start: (a) every replay (log at most once per 500 ms: part, ball, t*, depth, count;
   notification when more than two replays happen in one sub-interval); (b) an island that cannot be fully rewound yet (a bat, band or disc in it): the skip; (c) the force detector (a contact force far above what the
   relative closing speed of ball and surface explains, with the part's state), built; (d) every no-past seat (point 6).

6. A BALL WITH NO PAST (agreed, not built): a ball created inside a part, teleported into one by a script, or inside a part when Collidable turns True (gap already negative at the start of the sub-interval).
   Minimum translation, for this case only: move the ball along the normal of the deepest overlap to touching distance, repeated over every surface it overlaps, up to 8 passes; velocities unchanged; no
   stock; the playfield is just another surface of the loop (the 'seat would put the ball under the playfield' refusal goes away). If the ball is squeezed and does not fit, the remaining overlap is real and the
   force law carries it. Leaves open: ball control that drags a ball into a part is pushed out every cycle like a hard wall; a ball past the far side of a thin sheet is seated through to the wrong side.

What it would break (rule 7): walls and rubbers that use the ball-only rewind seat (results change slightly: re-run the matrix); the order of events within a sub-interval (parts' Hit/Switch after the stock collisions
of the same sub-interval is not the case: they move to after UpdateDisplacements, as stock); tables whose scripts depend on part events firing before the free balls move.

Build order (each step checked against the same harness): (1) point 1: done. (2) the dispatch reorder: DONE 2026-10-26 (ContactSystem::Finish split into FinishState (releases, band publish; in Step) and DispatchEvents
(ball-ball callbacks, part hits, the queue) run by ContactSystem::Dispatch(), called by PhysicsSimulateCycle right after UpdateDisplacements; the parts' own events (bumper Hit / Switch, gate and spinner events) are queued with
DeferEvent instead of fired in PartAdvance). Checked: gs8 event lines identical to the baseline (13 shots), bumper3 hits per shot identical to before. NOT checked: the ball-ball callback and rumble through the new
position, cost. Band and sling switch events still fire inside the band step (not queued): bands are not in the rewind until they implement SaveState. (3) SaveState / RestoreState
for the bumper, gate, spinner: DONE 2026-10-26 (ContactMovingPart::State = 2048 plain bytes, no allocation; HingeBody::Body::Dyn, Bumper::Dyn; offline test runs/2026-10-26-bumper/test_state.cpp: 11 parts, restored into the
same object and into a fresh one, bit-identical traces, plus an unrestored control that differs; bumper 297 bytes, gate 746, spinner 754; gs8 and bumper3 events unchanged). (4) snapshot at each sub-interval + snapshot_us in the cost log: DONE 2026-10-26. ContactSystem::SaveStart() (before Step) / RestoreStart(): every ball's position, velocity, spin; the engaged balls' contacts (whole entries
copy-assigned in place); the ball pairs; the saved state of every moving part; the event-queue size. The engaged list and the pair list now change only in ApplyReleases (releases and the pair clean-up moved from the end
of Step to the dispatch, after the free balls have moved), so a snapshot of their contents is complete. Self-test (VPX_SNAPSHOT_TEST=1: after every Step, restore and step again, compare balls / contacts / pairs / parts): gate and
spinner run 14,000+ steps, bumper run 6,000+ steps, 0 different; negative control (=2, parts left out of the restore): about 2,000 and 320 differences. Cost (focused, per sub-interval, VPX_CONTACT_TIMING snap_us):
bumper run mean 2.5 us, p99 7, max 99; gate run mean 1.8, p99 6, max 214 (23 and 27 rows of 7,098 and 13,568 at 10 us or more, with 0 or 1 engaged balls: not tied to the work, cause not found: OS jitter or a
rare allocation). Judged by the worst cycle the extra is up to 0.2 ms of the 1 ms; the mean is under 3 us. Bats and bands are not saved: their islands are not self-tested. (5) overlap check after UpdateDisplacements with the
time-of-impact bisect and the island replay. (6) no-past seat and the reports. (7) scenario matrix with pass / fail and cost: a free ball put 3 mm from a moving ring, two balls on one bumper, a ball between

7. ENGAGED BALLS ON MOVING PARTS (agreed 2026-10-27, not built). Why: a ball already touching a bumper, gate or spinner island is outside points 1-6: the island takes the uniform path (Substeps(), IslandStatic false), steps are
   planned once per cycle from BallStep, nothing is re-checked inside the cycle, and RwLate ignores contacts that were touching at the start of a substep. Measured: Bumper2 launch 11.4 m/s (5.2 J ball kinetic energy,
   80 g), Bumper4 3.66 m/s (0.54 J); ESTIMATED upper bound of the AE-23-800 coil work over the 10 mm stroke 0.18 J (28 V, 3.769 ohm, 15.77/5.26 mH, bobbin 35.3 mm, x0 0.3, full current from t=0): the integration created the
   energy, a real pinch could not.
   a) Same stepping for every island: bumper, gate, spinner islands use the arrival-stepping loop; the parts step inside it every substep; part state is saved and restored with the ball snapshot (SaveState exists).
   b) Step size from the RELATIVE velocity: ball velocity minus the part's actual velocity at the contact point, plus both acceleration bounds; a ball held by several contacts uses their stiffnesses summed; the part's mass
      enters the reduced mass.
   c) Every contact is checked every substep, not only first contact: depth beyond the impact depth of the relative closing speed triggers a rewind with a finer step (touching contacts included).
   d) If the depth is still too large at the minimum step, or at the rewind cap (16), the overlap is real: the force law carries it, a notification reports it, no velocity is edited.
   e) Energy detector (rule 8): per cycle a ball's energy gain must not exceed the work done on it by the part's drive plus its own starting energy; a violation = WARN + notification. Also the pass/fail of the scenario matrix.
   Before code: replay the recorded launch cycle with finer steps to confirm step size is the cause (ask the user first). Read the friction path (pinch / squirt-out) - not read yet.
   What it would break / leaves open (rule 7): cost (more substeps for a ball on a part, not measured, matrix includes timing); bats, bands, discs stay excluded (no SaveState, skip warning); friction and squirt-out untested;
   part event order inside a replay to define; several balls on one part untested; a part faster than its stated bound is only reported; the energy check is only as good as the coil model.

12. FLIPPERS, BANDS AND THE TURNTABLE DISC ON THE SHARED LOOP   (to-do 1.3; designed with the user piece by piece from 2026-10-28; nothing built)
--------------------------------------------------------------------------------------------------------------------------------------------
Why. contactsystem.cpp IslandRewindable() sends every island holding a bat, a band or a turntable-disc surface to the fixed-step path (Substeps(): the ini substep_us, 5 us,
for the whole 1 ms cycle, no arrival steps, no rewind, no depth check), even when the ball only has the disc within reach and touches nothing.
MEASURED (stress table, run_cost6_p1d: focused BGFX, 6 balls, phase 1, 20,000 cycles, cycles.csv): 1,160 cycles had their slowest island on that path, median 201
substeps and 176 us; by what that island touched: a flipper about 740, a band about 140, the playfield only or nothing (a ball beside the disc or near a bat) about 80.
A one-ball island touching only the playfield on the arrival path: median 19 substeps, 9 us. The ball beside the disc is the slowest island of the worst 7-cycle
window (7089 us from t=13840 ms, limit 3000).
Goal: each of the three becomes a ContactMovingPart (ModelStandards 2a) and its islands use SubstepsArrival with every shared guard (ModelStandards 2b); the bat,
band and disc special cases leave contactsystem.cpp. Pieces: 12.1 disc, 12.2 flipper bats, 12.3 bands and slings, 12.4 proof.

12.1 Turntable disc   (approved by the user 2026-10-28; BUILT 2026-10-28, checks in NewPhysicsReference.txt change log 2026-10-28 and below)
   a. What it is. The disc becomes a moving part like a gate (a host HitRubber with m_part; maths in a pure-SI header, so it joins the offline bench). The contact law
      stays ContactCore with the disc's surface velocity w x r, called through the part's ContactItem; the reaction is kept by the part.
   b. Law: Newton's third law at every substep. Inside the island's substeps (StepInIsland) the disc turns with the summed torque of its balls (friction, twist,
      rolling resistance about the axis), the motor torque and the bearing drag. The motor law is today's (linear torque-speed, Turntables::Step), solved exactly over
      each substep (the same exponential over h), so the result does not depend on the substep count. Today the disc holds its speed for the 1 ms and gets the balls'
      angular impulse at the end of the cycle (HitRubber::ApplyReaction -> Turntables::AddImpulse).
   c. Energy. Only the motor adds energy (its torque times the disc speed); the bearing drag and the contact remove it. Today's hold-then-push can create up to
      J^2 / 2I per cycle (J = the balls' angular impulse on the disc in the cycle): about 2.7 mJ for a ball landing at 1 m/s on the rim of the stress-table disc
      (800 g default, 64 mm, I = 1.64e-3 kg m^2) and sliding (CALCULATED, not measured). Stepping the reaction every substep removes that term.
   d. Closing speed. ContactMovingPart::SurfaceSpeedBound is defined as the fastest any point of the part's surfaces can move ALONG ITS OWN NORMAL (toward a ball),
      plus what the drive can add in the cycle. A disc turning about its own axis maps its surfaces (top face, rim) onto themselves: no point moves along its normal,
      so the disc answers 0. Gates, spinners and bumpers keep today's values (their full point speed, an upper bound of the normal speed). Without this the rim speed
      (2.2 m/s on the stress table: 325 rpm, 64 mm) would shorten arrival steps and widen engagement for no physical reason.
   e. Rewind. SaveState / RestoreState: disc speed and angle (and the part's stepped time). With no ball within reach the disc moves alone (AdvanceAlone = today's
      Turntables::Step); within a cycle the contact system and the turntable step share the time as for a gate (steppedS, steppedThisCycle).
   f. Several balls. Balls with the same disc within reach are one island (FindIslands links them, as for a gate), coupled through the disc. Two or three balls on a
      disc are common (user, 2026-10-28), so this is a normal case, not an edge case: they share the finest step any of them needs.
   What it breaks / leaves open (rule 7):
   - Cost: two or three balls on the disc share one island's finest step. Measured on the stress table with 2 and 3 balls on the spinning disc (12.4); INFERRED cheaper
     than today's 201 fixed substeps, not measured.
   - Table restart: the disc part must leave the part registry at table end (trap: turntable slowdown 2026-10-13, a host left across restarts). Checked by the
     restart case.
   - A ball over the gap rests on the playfield rim (static) and the disc rim (moving) at once: two surfaces in one contact, handled by the shared loop. Checked by the
     'ball at the disc edge / gap' case.
   - The new meaning of SurfaceSpeedBound: no change for gates, spinners and bumpers (INFERRED: their values already bound the normal speed). Checked by their matrix
     rows and the snapshot self-test.
   - The speed and angle the script reads (TurntableSpeed, TurntableAngle) and the drawn angle: read at the end of the cycle as now (INFERRED unchanged).
   - Turntable without playfield_contact = 1: the sections are ignored as today (no disc part is built).

12.2 Flipper bats   (approved by the user 2026-10-28)
   a. What it is. A model flipper (rubber contact on) becomes a moving part like a gate: a host HitRubber with m_part, its box the swept circle of the bat; the maths in a
      pure-SI part around ContactBat (contactbat.h is SI already), VPX units only in the adapter. The bat's rubber is one more SurfaceContact of the ball, with today's law
      (RubberContact::Evaluate on the bat outline) called through the part's ContactItem; its shear state is the item's state, saved with the snapshot like any surface's.
   b. Engagement. The contact system finds a ball approaching the bat itself (closing speed + SurfaceSpeedBound, point 11.1), as for every surface. Today the stock hit
      search finds the touch (hitflipper.cpp Collide -> ContactSystem::EngageBat), so every bat contact starts late and SetupBat seats it with a private rewind.
   c. Law: Newton's third law at every substep. StepInIsland(h): the bat turns with the summed torque of all its balls, its coil (plunger, link, both windings), the return
      spring and its stops, in its own substeps inside h (today 20 us, ModelStandards 3b). The stops stay as they are (impact law for them is to-do 2.2).
   d. Step size from the shared rule (NextStep, BallStep): the reduced mass of the ball and the bat's effective mass at the contact (InertiaSI() / lever arm^2) and the
      rubber's stiffness. Neither the ini substep_us (5 us) nor the bat's own 20 us cap sets the ball's step any more.
   e. SurfaceSpeedBound (along the normal, 12.1 d): tip speed now + (coil torque at full current + return spring) / smallest inertia x cycle x tip radius + the pivot
      nudge's present speed.
   f. Rewind. SaveState / RestoreState: phi, omega, plunger position and speed, both coil currents, lastAlpha, rigid, wasPreEos, coilOffPrev, plungerHitStop, hitL, the
      idle flag and its snapshot, the nudge pulse (nzActive, nzT, nzA, nzBaseX, nzVelU) and the pivot offset: about 25 values, well inside State's 2048 bytes.
   g. Removed from contactsystem.cpp: Body::bat, batLive, batRp, batOl, absCorr, pivOff, ctq, hitStop, noPairs; SetupBat (private rewind seat), BatForces (private release
      counter), StepBats, the loop that steps the bat after a trip, the bat branch of HandBack, DetachBat's own release rule. Their jobs go to the shared rewind (point 11.2),
      the no-past seat (11.6) and the shared release (release gap + bound x cycle).
   h. Energy. Only the coil, the return spring's preload and the pivot nudge (a prescribed pivot motion, so a drive) add energy; the contact, the link's free play and the
      stops remove it.
   i. Without balls the bat moves alone as now (AdvanceAlone = UpdateDisplacementsFlipper's stepping, idle dormancy kept). EOS / BOS events and the nudge start on the
      other bat stay where they are: after the step, from the bat's state (plungerHitStop, hitL).
   What it breaks / leaves open (rule 7):
   - The flipper's Hit event and rumble fire from the contact system's touch (a part Hit event, after the step), not from the stock collision: timing and speed values
     change slightly. Scripts that time on them: to check. Ball control's 'last flipper hit' (SetDraggedBall) moves with it.
   - Flipper ini keys rubber_release_steps and rubber_substep_us lose their role: listed in NewPhysicsReference.txt, notification when set (rule 8).
   - A ball pinched between a bat and a sling: the island holds a band and stays on the fixed path until 12.3 is built; reported on screen as the other skips (11.5 b).
   - Table end with balls on a bat: the part's teardown lets go of its balls (trap: crash at play end 2026-10-20, ReleaseBat, to-do 2.6). Checked by the restart case.
   - Flippers without the model (stock flippers): unchanged, stock until to-do 1.7.
   - Two balls on a raised bat (to-do 2.5): one island through the part, as today.
   - Cost: a ball on a moving bat still needs fine steps; the gain is mainly resting balls and balls beside a bat (INFERRED from the code, not measured).

12.3 Bands and slings   (approved by the user 2026-10-28, with the change in g: an out-of-range band is prevented, not handled)
   a. What it is. Each band becomes one moving part together with its sling plate, coil driver and switch blades (the plate's face and the band's nodes push on each
      other, so they step together). The maths move out of hitrubber.cpp into a pure-SI file (to-do 3.3; BandChain in rubbercontact.h is SI already), so bands join the
      offline bench. The ball's contact with the band keeps today's law (BandBallForce), called through the part's ContactItem.
   b. Law: Newton's third law at every substep. StepInIsland(h): the nodes move with the balls' reactions, the leg tensions and the plate's face; the plate turns with its
      coil and the band's push back; in the band's own substeps inside h. The node step comes from the shared step rule (ModelStandards 2c): the node's mass and the
      stiffness acting on it now (its legs' axial stiffness, the tension's geometric stiffness, a ball's contact), recomputed every band substep, not a count fixed once
      per cycle (m_bc.steps today; to-do 3.2).
   c. SurfaceSpeedBound (along the normal, 12.1 d): the fastest node now + the plate face's bound (coil torque at full current / plate inertia x cycle x face radius);
      a ringing node's speed is bounded by the band's stored energy (no node can move faster than that energy and the coil's work in the cycle allow).
   d. Rewind. SaveState / RestoreState: per chain the node count and order and each node's position, speed, peak, pinned flag and stop; the plate's angle and speed; the coil
      pulse timer; the switch blades. Nodes are added at engagement and when the band wraps a stop post inside a substep (BandChain::ApplyStops -> BandRebuild), so the count
      is part of the state. Size: up to kMaxNodes (12) per span, more for fixed nodes (band_node_mm >= 3 mm): about 6 KB for a long band, over the 2048 bytes of
      ContactMovingPart::State. So every part reports its largest state at table start and the snapshot reserves that once per part; no allocation during play.
      Gates, spinners and bumpers report theirs; nothing else changes for them.
   e. Events. The switch events (SwitchesUpdate) and SlingFire fire today from SlingAdvance inside ContactSystem::Step (before the substeps), against the rule that scripts
      never run inside the step (section 5). They go into the part's event list and are dispatched after the step with the other part events (point 11.2). The sling's
      own kick is the part's driver (no script), so its timing does not change.
   f. Energy. Only the sling coil adds energy. Leg tension stores and returns it; the viscous tension term and the contact remove it; a node pinned to a stop post gives
      its speed into the post. Coming off a post gains nothing (INFERRED; the offline step sweep checks it: energy may only fall unless the coil adds it).
   g. OUT OF RANGE IS PREVENTED (user, 2026-10-28: as rare as it might be, it is a break). Today a band is out of range when a node is not a number or deflects more than
      0.4 x its span's chord (BandDiverged, BandSubstepEnd); the band is then reset and its balls handed back untouched (a stock hand-back, not allowed). Two causes, each
      prevented by construction:
      1. Numerical (a node step too long for its stiffness: growth, NaN). Prevented by b: every node step is within the stability limit of the stiffness acting on that
         node at that moment; a ball's contact on a node enters through the reduced mass of ball and node.
      2. Physical (the ball or the plate really pushes the band past the model's valid range). The deflection a band can reach is bounded by the energy that can enter it:
         the balls that fit on the band, each at the launch limit (8 m/s, TestMatrixDesign section 1 limit 3), plus the sling coil's full work. At table start the part
         works out that deflection from its own tension law; if it is beyond the model's valid range the band is refused at load with a notification naming the key to
         change (rule 8): a check on the settings, not a cut-off in play. Objects behind the band (to-do 3.7) lower the bound further. Before building: find in the code why
         the valid range is 0.4 x chord (what the model assumes past it), and set the range from that reason.
      The deflection check stays in play as a safety net only (rule 2): a trip is a WARN + notification and fails the run (TestMatrixDesign limit 5); it retakes the substep
      with half the step through the shared rewind, and never hands a ball to stock.
   h. Without balls the band rings down on its own and sleeps at rest (AdvanceAlone; ModelStandards 3c; to-do 3.2). The drawn band (BandPublish, mesh animation) reads the
      part's state after the step. Band animation is broken today (user, 2026-10-28; to-do 3.9): not fixed by this design, and the band rows cannot be judged by eye until it is.
   What it breaks / leaves open (rule 7):
   - Switch and SlingFire script events fire after the step: same cycle, but their order relative to other events changes.
   - The energy bound in g.2 assumes the launch limit and the ball count on the band; a faster ball (a plunger shot straight into a band) is outside it: the safety net
     and the fast-ball watchdog report it. The 0.4 x chord reason is not known yet (to find before building).
   - Snapshot cost grows with the node count; fixed-node bands are the largest. Measured in the snapshot column of the cost log (snap_us).
   - A ball between a sling and a bat: one island with both parts once 12.2 and 12.3 are built. Two balls on one band: one island, as today.
   - Tables with unified = 0 keep today's band stepping (BandAdvanceCore) until to-do 10.3 is decided.
