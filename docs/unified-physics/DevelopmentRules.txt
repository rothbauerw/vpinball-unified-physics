DEVELOPMENT RULES for the physics work (branch unified-physics)
==============================================================
Set by the project owner. They apply to every change, by a person or an assistant. A change that breaks one of them is reverted, not defended.

1. NO FIX WITHOUT DATA
   a. A fault is understood when it is REPRODUCED (a deterministic replay in the harness, from the state in the log) or when the log/measurement itself PROVES the mechanism. A plausible story from the
      code and a few numbers is a hypothesis, not a finding.
   b. Write down what is MEASURED and what is INFERRED, separately, and say which is which when reporting. Never present an inference as the cause.
   c. Before touching engine code, test the hypothesis against the data already in hand (the per-cycle timing CSV, the trace, the watchdog log). If the data contradicts it, drop it.
   d. Engine code is not edited to "try" a theory. Temporary instrumentation is allowed: mark it /* TEMP */, keep it out of the commit, remove it when done.
   e. Order of work for a reported fault: collect the log -> build the timeline -> check every cheap source -> replay the exact state -> locate the mechanism with instrumentation -> only then fix.
      When the user's play feels wrong, first check the table's ini and the log: which model and which values actually ran. Reproduce on the table where it
      happened, unchanged, before building any test scene. A simplified scene may be used to isolate a mechanism; a fix is proven on the real model and table.
   f. If a reported fault cannot be reproduced, add always-on, cheap diagnostics (like the fast-ball watchdog) and wait for the next occurrence. Do not "fix" what cannot be seen.

2. NO HACKS
   A fix names the PHYSICAL LAW behind it. No speed cutoffs, forced stops, position snaps, clamps that hide a symptom, per-scenario constants or special cases per source (bat / band / pair / ...).
   If a law already exists in the code, find out why it is not acting before adding anything. A safety net is allowed only as a net, never as the fix, and it recovers inside the contact system.
   NOTHING IS EVER HANDED BACK TO STOCK IN A NEW MODEL (user, 2026-10-26, repeated 2026-10-30). Stock is only the development fallback for object types not yet converted.

3. GENERAL FIXES, PROVED ON A MATRIX
   Fix the general rule, grep for every other place with the same special case, and prove it on the test matrix (docs/unified-physics/TestMatrixDesign.txt: fixed limits per run, cases per model, stress table)
   with numeric pass/fail including the cost per cycle. A fix is done when the matrix passes, not the one scene. The old scenario matrix (runs/2026-10-09-slow-contact: batch_matrix.ps1,
   matrix_compare.py) was judged a fail by the user on 2026-10-27 and is not used. The accuracy part of the new one exists (the 750-hit bench against a 1 us reference); the performance tests are not built
   (to-do N10). Say which checks were run.

4. RUNS
   Group several changes before a full regression; the user decides when a matrix is run. Timing and event-timing tests run focused (run.ps1 -Focused) and the user is told first so the machine is idle.
   Always call run.ps1 with explicit full paths and check the ini that was loaded.
   How to build, run and diagnose: docs/unified-physics/TestingPlaybook.md (read before any test).
   Bench first. VPX only through the test driver, for one named question. The bench must match VPX, so moving to VPX is a formality (user, 2026-10-31).
   Design every measurement a test needs up front, down to the cause, and save everything a run computes, so follow-ups need no rerun.
   Time one case alone before a batch. Long runs log progress and a time-left estimate from measured timings, never a guess.
   A session may close VPX to test, unless the user has said they are using it.
   A test that starts with a ball inside a ball or an object is a broken test, never an engine fault.

5. PERFORMANCE (the one cost rule; ModelStandards section 4 points here)
   Every model is tuned for speed: measure the cost per cycle (VPX_CONTACT_TIMING), expose knobs.
   Physics, the table script and the frame preparation share one thread; at 144 Hz a frame (6.9 ms) holds about 7 physics cycles.
   Per object (user, 2026-11-06): 30 us in EACH 1 ms cycle for the object with the ball(s) on it; the worst cycle counts. Not a 7-cycle window, not other objects.
   Frame (user, 2026-11-03): physics over any 7 consecutive cycles <= 3 ms, ball piles included; within 0.2 s after a hit event (a landing, a flip, a fast ball
   into a pile) up to 10 ms per 7 cycles. Single cycle <= 1.5 ms: proposed, not confirmed by the user.
   Judge by the worst cycle and the worst window, never the average.

6. DOCUMENTATION AND HISTORY
   Every feature, key, script call and environment variable goes into docs/unified-physics/NewPhysicsReference.txt with a dated change-log entry, in the same change. Names follow the physical part (flipper, sling, rubber), never a table.
   Nothing is committed or pushed until the user says so. Convention differences from stock VPX are stated and documented.
   New work goes behind an ini setting, on by default while it is tested; 0 gives the old path unchanged. Once the user accepts the new path, the old path and its
   setting are deleted after the code is committed (the change log names that commit); ask first only if removal is high risk or later A/B tests need it.
   A dropped idea's code and setting are deleted. Private source copies only for offline test programs.
   Every item the user states goes into the to-do list at once; the to-do list is the single source of open work.

7. WHAT BREAKS, AND WHAT THE DESIGN DOES ABOUT IT (user, 2026-10-13)
   a. Every new design and every fix includes a step that lists the scenarios it would NOT handle or would break: other sources of the same case, other objects and modes, restart and teardown, extreme values
      (zero, huge, many balls), order of events, a table without the feature, a second use in the same process.
   b. Where it is possible, the design handles or prevents those scenarios (an ownership rule, a guard that is a safety net, a test in the matrix). Where it is not, the limit is written down in
      docs/unified-physics/NewPhysicsReference.txt and the to-do list, with the reason.
   c. The list is part of the report: say which scenarios were checked, how (measured or only reasoned), and which remain open. A scenario that is only reasoned about is marked INFERRED (rule 1b).

8. UNWANTED OR TRACKED BEHAVIOUR IS SHOWN ON SCREEN (user, 2026-10-13)
   The user does not read vpinball.log. Whenever the engine detects behaviour that is unwanted or that we track (a leak, a tripped safety net, a hand-back to stock, a budget overrun, a fast ball, an
   ignored ini key), it raises a notification on the playfield (m_liveUI->PushNotification, text says what, where and what to do) AND writes the same text to the log as WARN. The detector is always on
   and cheap (rule 5), never silent. A notification is raised once per cause per table start, not every cycle. Behaviour that is only a diagnostic number stays in the log/CSV.

9. FINISH THE MODEL FIRST (user, 2026-10-31)
   a. A model still being built: first build what is missing and make each piece of the model do its job. A piece that does not work is model work, not a side issue.
   b. Other faults may only be a result of the model being incomplete. Note them and recheck them once it is finished, unless one stops the model working.
   c. Cost is measured and tuned once the model works, unless it stops the model working or is a real question whether the model is feasible.
   d. The cost in rules 3 and 5 and in ModelStandards section 7 applies when a model is called done, not on each fix.

10. STRESS TESTS (user, 2026-11-01; defines "push the engine until it breaks" in ProjectLeadBrief.txt)
   a. When: once per model or law change, when it already works on typical hits and before it is promoted; and when a specific failure is suspected. Never for routine changes.
   b. What: a small fixed stress set for that part, about 10 - 20 shots with a time cap: 6 m/s (twice the extreme), grazing hits, deep overlap starts, repeated hits, stacked contacts, a few step sizes.
   c. Always a fault, at any input: a crash, a launch, an energy gain, a solver that hangs. Anything else outside typical is recorded, not fixed, unless it points to a fault that also affects typical play.
   d. Every failure is saved as a repeatable case. Only cases that found something join the set.

11. TESTING IS CAPPED AND THE BUILD GOES TO THE USER FIRST (user, 2026-11-01, after two leads in a row broke the testing rules and kept the user waiting over an hour)
   a. The user's time comes first, and the user's play is the real test. As soon as a model builds, loads and does its job on a table, the session stops and the build goes to the user, before any test list.
   b. A test goes in a brief only if its result changes a decision being made now. A list approved earlier is not carried over whole: each item is justified again or left out. A left-out item is noted, not run.
   c. Every session brief carries three lines. DECISION: what result changes which decision. TOTAL CAP: runs and wall minutes for the whole job, not per run; default 10 runs or 15 minutes, whichever comes first; more needs the user's OK before it starts. HAND OVER: the point the session stops and the build or answer goes to the user. A hook refuses a brief without them (.claude/hooks/check_brief.py).
   d. At the cap a session stops and reports, even part way. No grid, sweep or second batch without the lead's OK. The lead gives it only for a named benefit and tells the user.
   e. Before starting, the lead tells the user how long they will wait. On every note from a running session the lead reads its run count, elapsed time and context, and stops it at the cap. Never relay "still running".
   f. A cap and a list do not make a test worth running. The lead answers for what is in the brief; the hook only checks the lines are there.
   g. The lead checks that a brief's commands and bench features exist before sending it, and checks time and cap claims against the real clock before passing them on.
