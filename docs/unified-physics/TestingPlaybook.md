# Testing playbook

How to build, run scripted VPX tests, diagnose and measure. Moved word for word from memory on 2026-11-07; updated in the same change as the harness.

Learned 2026-10-09 the hard way; each session was re-learning this. Keep it updated (add a line whenever a test costs you time). Related: [[may-close-vpx-to-test]], [[project-slow-contact-2026-10-09]], [[unified-surface-contact]].

**USE THE REAL BENCH FIRST (2026-10-31).** `runs/2026-10-31-real-bench/` (`README.md`, `RESULTS.md`): VPX itself with `VPX_BENCH=1`, no frames, no window, no lock, many at once. Same table, ini and driver file as a VPX run; `balls.csv` was byte-identical to VPX on 6 cases (stress p1-p3, Sling, Gorgar parts and rings), 5 to 24 times faster (stress p1 about 6 s, Sling 68.5 s in about 4 s). Scripted runs below are for what the bench doesn't cover.
- Bench pitfalls (2026-11-02, cost the user Windows errors on screen): run `bench.ps1` from the PowerShell tool or a script file, never through Bash with `C:\...` paths, because Bash strips the backslashes (a folder named `PinballVPX-Physicsruns...` is this). Not "many at once" on a table new to `runs\_tables`: the first runs race on `INDEX.csv` and the copy, so run one first. When editing a copied script, check each path with `Test-Path`. Confirm a run really started: `Test driver: N actions`, N above 0. No runs that might show a window while the user is playing.
- Private build check (2026-11-02, a 4-file build of a 45-file header change went to the user's play): after `bench_build.py`, compare its compiled count with `grep -l` of every changed header's includers; a shared header missed means a mixed exe with no error. Lead checks the count before any run counts.
- One renderer (user, 2026-10-31): physics is identical between GL and BGFX (6 stress p1 runs across both, one md5). Test on BGFX only, the build the user plays; build or test GL only for a renderer question. Never run a check on both.
- Run: `powershell -ExecutionPolicy Bypass -File runs/2026-10-31-real-bench/bench.ps1 -Name x -Exe <...>\main_exe\VPXBench_BGFX64.exe -Table <full> -Ini <full> -Drive <full> -Dir <your runs folder>`. No VPX lock needed. The `VPXBench_*` exe name keeps run.ps1 and wait loops from taking it for a VPX.
- Private copy, about 2 min: copy its `src\`, patch it, `python bench_build.py bgfx <out> <folder holding src\> <changed .cpp names>`, then run `<out>\exe\VPXBench_BGFX64.exe`. Its objects snapshot must match that `src\`; `bench_snapshot.py` refreshes both after main is built. A changed header: list every .cpp that includes it.
- Doesn't cover (use a VPX run, kept brief, for these): cost against limit 6 (the report's cost is bench cost), drawing and meshes, real input, table restart and teardown. Not yet compared with VPX: magnets on, scripts that act on the game, script and frame timers, drop targets (they fall per frame). ROM tables are out. A case with address-order splits (Gorgar pile, `hitball.cpp:238`) doesn't repeat on the bench either, as in VPX.

**Script patterns that work**: write results with `fso.OpenTextFile(OUT_DIR & f, 8, True).WriteLine`. A fresh ball: `Set b = BallRelease.CreateSizedBallWithMass(25, 1)`, `BallRelease.Kick 90, 8, 0`, wait ~120-400 ms, THEN teleport (`b.X/Y/Z`, `b.VelX/Y/Z` in U/VPT, 1 m/s = 18.53, zero `AngMomX/Y/Z`). A ball can get captured by a kicker after the kick and then ignores teleports (frozen): reuse ONE ball, kick it out of a captured kicker with `Kicker.Kick`, replace only if `b.Z < -50`. `b.DestroyBall` destroys a ball; `BallRelease.DestroyBall` does NOT destroy a free ball. Only one ball fits in a kicker; extra balls fall through. Use `kicker.BallCntOver`, `kicker_Hit` events for capture. Scripts: gsling2.vbs (24 sling shots), gsw15f.vbs (kicker capture from below, the reference kicker test), rest_flat.vbs / drop.vbs / slow4.vbs / pinch*.vbs, noop.vbs (just writes done.txt, to read load logs).
- Always compare against stock (feature off) in the SAME harness, same script, and count over many shots; single shots are chaotic (random hit order/scatter).

**Diagnostics (env vars)**: VPX_CONTACT_TRACE=1 (old name VPX_RING_TRACE still works; ContactEngage/ContactRelease/ContactTrace per cycle, depth per rubber), VPX_CONTACT_LOG=<csv> (every collision C / resting contact T of the FIRST ball with object type (21=kicker, 18=primitive/rubber, 0=wall) and name: great for "what is the ball touching"), VPX_CONTACT_NEAR=x,y,r (old VPX_RING_NEAR works; faces near a point + RubberNearTri vertices), VPX_PHYS_TIMING=<csv> (S rows; its sim_sum column MISLED me: for cost use per-phase timers, then delete them), VPX_RING_NOSIDE, VPX_RUBBERS_LOG. Crash reports: tables\basic\crash.txt (+crash.dmp) in the table's folder, top frame names the function.

Temporary instrumentation: mark `/* TEMP */` and grep before finishing; a `//` comment after code swallows a closing brace. When editing files with python, match the file's line endings (the repo is CRLF-ish; edit via exact-string replace helpers). **Ball mass (user's own tests, 2026-10-09):** the user tests KICKERS with ball mass 1 and RUBBERS (posts, wall/primitive rubbers) with ball mass 100. Reproduce with the same mass: scripts take it from the harness (`run.ps1 -Mass 100`; put `BALLMASS` in `CreateSizedBallWithMass(25, BALLMASS)`; rshot.vbs does, older scripts hard-code 1). A mass-100 ball loads rubbers 100x harder (depths ~10-30x, pinch settles slowly: 20 s at m100), so results at mass 1 do not predict mass 100. When the user reports a rubber problem, test at mass 100 AND 1.

**Harness traps found 2026-10-09 (each cost an hour):**
- A bash helper function wrapping run.ps1 (`run() { ... -Ini "$I\$3" ...}`) produced a wrong -Ini path in some runs: the ini was missing, VPX wrote a DEFAULT flipper file over it (log: "Flipper: wrote default settings to run_Xpx_physics.ini"), the rubber model was OFF and every result looked like stock. ALWAYS call run.ps1 with explicit full paths (no helper function) and CHECK `grep -c "\[Features\]" run_X/vpx_physics.ini` and `grep "loaded from" run_X/vpinball.log` (not "wrote default settings").
- Teleporting a reused ball: a ball still engaged by a rubber contact keeps its stale contact set, then hits the next rubber with a dead stock bounce. Use a fresh ball per shot (b.DestroyBall, create, Kick, wait 300-500 ms, teleport) for impact tests; reuse one ball only for kicker tests (kick it out).
- Do not place test balls inside rubber loops/posts (Kicker1 at (448.7,959) sits 63 U from Rubber3 at (512,949)): overlap start positions give nonsense (deep-overlap seat) that is not a play scenario. Check start spots against the table layout first.
- When the user is working, VPX windows left open lock the exe: close them (permission given) and say so.
- **Script sampling is coarse when VPX runs unfocused** (VPX_PLAY_UNFOCUSED=1 throttles frames, so the 1 ms script timer fires once per frame, rows can be ~200 ms apart): do not compute rebound ratios from the script's ball.csv then. Use the physics-rate logs instead: with trace on, `RingEngage <host> ... vn_in X` followed by `RingRelease <host> ... speed Y` gives e = Y/X per impact (drop test: the first entry is the ball's creation drop at t~1500, ignore it).
- **Check the table file before blaming the code** (2026-10-09): Rubber Test 2 was accidentally edited (playfield primitive renamed/duplicated -> plane + second floor) and gave dead drops. A mesh-playfield table must log `Primitive playfield_mesh: rubber force model on`; a plane table logs `Playfield: force model on` from PhysicsEngine::AddCabinetBoundingHitShapes. If the log shows the wrong one for the table you think you are testing, the table changed. Compare `cmp` against the table an earlier run used: since 2026-10-27 each run folder's t.vpx is stored once in runs\_tables\<hash>.vpx (run_X\t.vpx.removed.txt names it; runs\_tables\INDEX.csv lists all), since 2026-10-27 run.ps1 no longer copies the table: run_X\t.vpx is a HARD LINK to runs\_tables\<hash>.vpx (new tables are added to the store and INDEX.csv on first use; run_X\t.vpx.table.txt names the source table and hash; if linking fails it copies and writes t.vpx.copy-warning.txt). Never edit or save a run's t.vpx in the editor: it is the shared store copy. Backup of the old script: run.ps1.bak_2026-10-27_tables.
- `VPX_CONTACT_LOG` names the stock plane 'Table1'-style with obj type 0 (HitPlane never sets m_ObjType): a type-0 entry named after the table is the playfield plane.

**ANTI-HUNG TIME SKIP (found 2026-10-11, fixed for the harness):** the engine skips simulated time forward whenever a frame takes > 200 ms (PhysicsEngine.cpp "Anti hung mechanism"). The unfocused harness (VPX_PLAY_UNFOCUSED) runs ~190 ms frames, so before this fix only ~25% of game time was simulated (RingTrace showed ~150-cycle gaps; log timestamps 4 ms apart while t jumped 160 ms). Anything measured over game time with the old exe (decay rates, settle times, swing damping, timings) was SLOW by up to 4x: results from runs before 2026-10-11 10:50 that depend on elapsed game time are suspect (the "loaded damping" mystery was exactly this). Fix: the skip is bypassed when Player::PlayUnfocused(). Check for it in any run: `grep -o "RingTrace t=[0-9]*" log | awk` gap counter should be ~0.

**Parts-check lessons (2026-10-31, runs/2026-10-31-parts-check):** (1) `run.ps1 -Drive x.txt -Vbs evt.vbs` works together: ball motion from the driver (per-ms balls.csv), the script only logs events (GameTime - engine time at driver t=0, e.g. 602 ms, = driver time; the offset can be off by 10-20 ms, count events in windows shifted by -100 ms). (2) A gate/spinner plate swings 3-8 s: space shots 5 s (gate) / 8 s (spinner) or the next shot starts on a moving plate. (3) A PowerShell function named `R` is shadowed by the alias `r` (Invoke-History): name helpers `Run1`. (4) Another session's VPX can be open: wrap each run in a wait-until-none loop, never close it. (5) Start spots next to walls give instant bounces (spinner side shot began on Wall2): check the first 5 ms of a shot before trusting it. (6) Old-law exe vs new on the same ini: old keys act in the old exe only. (7) dumpvpx.py (olefile) reads object positions/rotations from a .vpx. (8) Offline hinge benches need `/FIcassert`; disc_test.cpp needs shearZeta -> shearTan.
**Offline Python with pair_hybrid:** pair_hybrid.py parses sys.argv[2] at import, so scripts importing it take ONE argument (e.g. theta/gaps). Files written via python heredocs keep CRLF; normalise before string replace. A "\n" inside a C++ string written from Python came out as a real newline once (cause unknown): use std::putchar(10).

## 3D magnet field reference (NGSolve)

User approved the download 2026-10-14 (PyPI: ngsolve 6.2.2608, netgen-mesher 6.2.2608, netgen-occt 7.8.1, ngsolve-openblas 0.3.33, ~50 MB, LGPL).
Installed in a venv with system site packages: `C:\Pinball\VPX-Physics\runs\.venv-fem\Scripts\python.exe` (main Python untouched).
Model: `runs/2026-10-14-mirror/ng3d.py` (A-formulation H(curl), nograds, Newton with symbolic linearisation, same B-H curves as fem.py; force by virtual work over the air layer touching a ball). First check: one ball, c19, NI 6200, 1 mm gap: 0.979 of the axisymmetric FEM; 406k dofs, ~3 min per solve, 6 Newton steps. Machine: 32 GB RAM; single-ball solves fit 3-4 in parallel, 2-ball solves only 1 (see Limits).
Why: the axisymmetric fem.py cannot do tilted/side balls; the earlier 3D BEM is linear only. Related: [[todo-and-parking-lot]].

Limits (measured 2026-10-15): a 2-ball case at ~557k dofs commits ~15 GB, so run NG_JOBS=1 (default in the scripts) with ngsolve TaskManager threads (~5.5 min/case). At ~1.0M dofs sparsecholesky fails ("bad array new length") and umfpack needs >23 GB; pardiso is not installed (MKL). Larger meshes need an iterative solver (CG + BDDC).
